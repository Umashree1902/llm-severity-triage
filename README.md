# Trusting AI in Defect Triage: Agreement, Consistency and Bias in LLM Severity Labels

QM640 Data Analytics Capstone — Walsh College  
Author: Umashree Pandiarajan

## Purpose
This project evaluates how far QA teams can trust severity labels that large language models (LLMs) assign to software defects. It measures:

- **RQ1 – Agreement:** LLM severity vs. human triagers, interpreted against agreement between two independent reviewers who re-label a 152-defect subset
- **RQ2a – Repeatability:** label stability when the identical prompt is repeated
- **RQ2b – Prompt sensitivity:** label changes when only the wording of the prompt changes
- **RQ3 – Bias:** over- or under-escalation, and the effect of product context
- **RQ4 – Guardrails:** effect of severity definitions and confidence-based deferral on correctness and calibration; the threshold is set on a validation subset and evaluated once on untouched test defects, including missed critical (S1) defects

## Models
- **Open-weight (done):** Llama 3.1, 8B (`llama3.1:8b` via Ollama), zero-shot, default decoding settings
- **Commercial (done):** GPT-4o mini, fixed snapshot `gpt-4o-mini-2024-07-18`, via the OpenAI API, zero-shot, default settings
- **Baselines:** majority class; TF-IDF (1–2-grams) + multinomial logistic regression trained on 2021–2024 defects

## Data
Public defect reports from Mozilla Bugzilla (https://bugzilla.mozilla.org), retrieved through the Bugzilla REST API.

- Primary sample: defects filed 1 January 2025 – 30 June 2026 with severity S1–S4
- Baseline set: defects filed 2021–2024, used to train the TF-IDF baseline and, if the optional retrieval extension runs, to supply similar past defects (no overlap with the primary sample)
- Stratified sample: all 98 eligible S1 defects plus 800 each from S2–S4 (2,498 defects), with subsets for RQ2 (469), RQ3 (825), RQ4 test (470), threshold validation (201) and the reliability check (152)
- Excluded: tasks, enhancements, defects without a description, security-restricted reports, automatically filed intermittent test-failure reports, and defects whose severity changed in the 30 days before extraction
- Reporter names, emails and user handles are removed during cleaning

See [`data/data_dictionary.md`](data/data_dictionary.md) for all variables.

## How to run

### 1. Setup
Requires Python 3.10+.
```bash
git clone https://github.com/Umashree1902/llm-severity-triage.git
cd llm-severity-triage
pip install -r requirements.txt
```

### 2. Reproduce all results from the stored data (about 5 minutes, no network or GPU needed)
```bash
cd src
python eda.py                # -> EDA figures 1-8, eda_summary.json
python baseline.py           # -> baseline_metrics.json, predictions_baseline.csv, figure 9
python evaluate.py           # -> results/llm_metrics.csv, figures 10-12
python evaluate_rq2_rq4.py   # -> results/rq_tests.json (incl. population-weighted kappa, RQ4 CIs), figures 13-16 per model
```
Expected key outputs (Llama 3.1 8B, P1, 2,498 defects): weighted kappa 0.247, macro-F1 0.222;
RQ2 flip rate 34.5%; RQ4 test accuracy P1 0.302 vs P2 0.306.

### 3. Re-run the full pipeline from scratch (about 1 day, mostly LLM calls)
```bash
export BUGZILLA_API_KEY=...            # optional; raises Bugzilla rate limits
cd src
python extract.py                      # full extraction (about 15-25 minutes)
python clean.py                        # exclusions, derived variables, stratified sample and subsets
python eda.py                          # summary statistics and figures
python baseline.py                     # TF-IDF + logistic regression and majority-class baselines
cd .. && ollama pull llama3.1:8b
OLLAMA_NUM_PARALLEL=2 ollama serve &   # local model server
bash run_all_llm.sh                    # all conditions (about 7,600 calls), then both evaluation scripts
# commercial model (OpenAI-compatible API); the key stays in your shell, never in the repo
export LLM_API_KEY=sk-...
PROVIDER=openai MODEL=gpt-4o-mini WORKERS=4 bash run_all_llm.sh
```
All random draws use seed 42. `run_llm.py` can be stopped and restarted; completed calls are skipped.
A fresh extraction draws from the live Bugzilla data, so counts can differ slightly from the stored sample.

## Database
`python src/build_db.py` loads everything into one SQLite file, `data/severity_triage.db` (about 5 seconds; not
committed, rebuilt from the CSV/JSONL files). Tables: `defects`, `defect_subsets`, `training_defects`,
`population_counts`, `duplicate_pairs`, `baseline_predictions`, `llm_runs`, `severity_levels`; views
`v_llm_vs_human` and `v_agreement`. Example:
```bash
sqlite3 data/severity_triage.db "SELECT * FROM v_agreement WHERE run_id = 1;"
```

## Triage assistant (deployment prototype)
A FastAPI service that suggests a severity for a new defect and routes it to a review queue
(`priority-review`, `review` or `suggest`). It never sets the severity itself; a triager confirms.
```bash
pip install -r requirements.txt -r app/requirements.txt
LLM_PROVIDER=ollama LLM_MODEL=llama3.1:8b uvicorn app.main:app --port 8000   # open http://localhost:8000
# without an LLM:  LLM_PROVIDER=none uvicorn app.main:app --port 8000
# with Docker (assistant + Ollama): docker compose up -d && docker compose exec ollama ollama pull llama3.1:8b
```
Endpoints: `POST /api/triage`, `POST /api/triage/{id}/decision`, `GET /api/log`, `POST /webhooks/bugzilla`,
`POST /webhooks/jira`, interactive docs at `/docs`. Tests: `LLM_PROVIDER=none pytest -q`.
Offline evaluation of the routing policy on the study data: `python src/evaluate_policy.py --model gpt-4o-mini-2024-07-18`
(recommended second opinion: with GPT-4o mini, 3 of 98 S1 defects reach the low-risk `suggest` queue, against 11 with Llama).
Paired comparison of the two LLMs and TF-IDF: `python src/compare_models.py`.
Architecture diagram: `docs/architecture.svg`.

## Human label reliability check
`python src/make_reliability_sheets.py` creates two blind labelling workbooks (152 defects, 38 per severity, neutral
item codes, a different order per reviewer, stated severities redacted) in `data/reliability/`. Put the two returned
workbooks in `data/reliability/returned/` and run `python src/reliability.py` for inter-reviewer agreement and
kappa, each reviewer against the Bugzilla label, and both LLMs against the reviewers (`results/reliability.json`).
